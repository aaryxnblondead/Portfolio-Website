The problem: Campus recruiters at a tier-2 engineering college in Mumbai receive 1,000+ resumes in a single placement cycle, all in PDF format with inconsistent templates. Hiring teams spend hours extracting skills, experience, and contact details manually.

The constraint: The NER model had to handle Indian naming conventions, universities with varied spellings, and non-standard date formats, all without a GPU.

What I built: QualifyAI separates batch resume ingestion from real-time candidate search. A FastAPI backend parses PDF and DOCX files, applies NER and semantic embeddings, enriches skills with Gemini when configured, and stores structured records in PostgreSQL. ChromaDB powers similarity search while a React frontend exposes candidate data and visual analytics.

The design decision was to keep expensive work asynchronous: Celery handles ingestion, the query layer stays responsive, and Redis is optional infrastructure rather than a hard dependency for basic use. Production runs on AWS with ECS Fargate containers behind an Application Load Balancer, RDS PostgreSQL for relational data, and Elastic File System (EFS) for uploaded resumes and vector storage.

The architecture separates the ingestion pipeline (batch processing) from the query layer (real-time), and I implemented a caching layer for repeated entity extractions to keep the OpenAI cost under $15 per 100 resumes. Production secrets are injected via AWS Systems Manager Parameter Store — no secrets are hardcoded in container images.

**Key technologies:** FastAPI (backend), React + Chart.js (frontend), spaCy for NER, Sentence Transformers for embeddings, ChromaDB for vector search, Celery for async ingestion, Alembic for migrations.

**Production engineering challenges:**

- **IAM AccessDenied** on ECS task startup — fixed by adding CloudWatch Logs write and SSM `GetParameter` permissions to the task execution role, plus ECR image pull actions.
- **Host-not-found** between frontend and backend containers — resolved with AWS Service Connect for stable internal DNS.
- **EFS mount `ResourceInitializationError`** — corrected by enabling VPC DNS hostnames and creating EFS mount targets in every subnet used by Fargate tasks.
- **504 Gateway Timeout** from ALB — traced to security group gaps blocking the ALB-to-task network path; fixed with least-privilege ingress rules.

What broke: The first deployment failed on resumes with two-column layouts because PyMuPDF concatenated both columns into a single text stream, which broke the entity boundaries. The fix required switching to a layout-aware PDF parser (pdfplumber) and adding a preprocessing step that detects column gutters.

The second issue was less obvious: Indian university names vary wildly in their English spellings. "Fr. Conceicao Rodrigues College of Engineering" sometimes appears as "FCRCE" or "Rodrigues College." The NER model kept missing these, so I added a fuzzy string matcher against a seeded university registry with 200+ Indian institutions.

What I'd do differently: Build the university registry before the ingestion pipeline. The entity accuracy was bottlenecked on domain-specific normalization, and I kept bolting fixes onto the extraction layer.
